## 3. Gate 3: AST-Diff Structural Check
Implemented in `src/tools/verify_gates.py` as `gate_ast_diff_check`.
- **Mechanism**: Extracts top-level declarations using `src/ast_parser.py` (`parse_clang_ast`). Compares function names, return types, and parameter types before and after the patch.
- **Fail Conditions**:
  1. A function was removed (`function_removed`).
  2. A function's signature was altered (`signature_changed`).
  3. An unexpected new function was added (`unexpected_function_added`), unless that function was already declared/defined in the pre-patch source text and was merely unblocked by fixing an unclosed brace/bracket or missing header.
- **Verification**: 6 synthetic unit tests in `tests/week8_verification/test_gate3_ast_diff.py` covering all pass/fail conditions and independence from clean compilation. All 6 tests pass.

## 4. Gate 4: Security Regression Check (Location-Aware)
Implemented in `src/tools/verify_gates.py` as `gate_security_regression_check`.
- **CWE-457 Scanner Hardening**: Fixed `security_analyzer.py` so variables initialized via:
  - Stream extraction on `istream` (`cin >> x`, `std::cin >> x`, chained `cin >> a >> b`, `ifstream >> x`),
  - C-style `scanf`/`fscanf`/`sscanf` with address-of (`&x`, `&var`),
  - Stream string extraction via `getline(cin, s)` and `std::getline(std::cin, s)`,
  are correctly tracked as initialized rather than flagged as uninitialized reads. Genuine CWE-457 cases (`sec11_uninit_use.cpp`, `sec21_uninit_branch_leak.cpp`) continue to be reliably detected.
- **Location-Aware Diff Mapping**:
  AST-based detectors are partially blind on files that don't compile, so pre-patch counts are artificially low. Gate 4 maps pre-patch findings to post-patch line coordinates using `difflib.SequenceMatcher`:
  - **Fails ONLY IF**: A new finding appears within **±3 lines** of a patched hunk, or represents a vulnerability type the patch plausibly introduced (e.g. injected `strcpy`, `strcat`, `system`, or a variable introduced in the patch).
  - **Advisory Unmasking**: Findings that appear distant from the patch hunk because the file now parses cleanly are returned in `details["unmasked_findings"]` as advisory warnings and do not fail the gate.
- **Verification**: 7 unit tests in `tests/week8_verification/test_gate4_security_regression.py` covering clean patches, injected `strcpy` on its own line (fails), null dereference (fails), pre-existing warning tolerance, unmasked distant uninitialized reads (passes with advisory finding), and independence from compiler error status. All 7 tests pass.

## 5. Gate 5: Differential Execution Test Assessment
Implemented in `src/tools/verify_gates.py` as `gate_differential_execution`.

### Applicability Finding: 0 / 56 Repair Targets
- **Finding**: Differential execution is applicable to **0 / 56** repair targets in the benchmark suite.
- **Reasoning**:
  1. All 56 repair benchmark targets have `expected_status == 'error'`. By definition, they do not compile prior to repair.
  2. Because the pre-patch file fails compilation, no pre-patch binary exists to establish a behavioral baseline.
  3. Clean files (`cl01-08`) compile cleanly but produce no repair diagnostics; optimization files (`opt01-04`) compile cleanly but exercise `optimize()`, not `repair()`.
- **Reporting Implementation**:
  - When there is no pre-patch baseline, `gate_differential_execution()` returns `status="not_applicable"` and `passed=None`.
  - The verification pipeline (`verify_patch_gates()`) and structured `trace_log` report Gate 5 as `status: "skipped"`, allowing valid repairs to pass without obstruction.
- **Applicable Path Verification**:
  Verified with warning-only C++ source files (clean exit code 0 pre-patch):
  - A behavior-preserving patch passes (`status="passed"`, `passed=True`).
  - A behavior-altering patch fails (`status="failed"`, `passed=False`, `failure_condition="output_mismatch"`).
  Tested in `tests/week8_verification/test_gate5_differential.py` (4/4 tests pass).

## 6. Part 4: Pipeline Integration — `verify()` Wired into `planner.py`

### Architecture

The `Planner.run()` loop now follows this pipeline for every repair candidate:

```
understand(file) → detect(model) → repair(model, finding) → verify(model, patch) → apply-or-rollback
```

Key integration points:
- **`src/tools/verify.py`**: Replaced the minimal compilation stub with the full 5-gate orchestration via `verify_patch_gates()`. Returns `VerifyResult` with `gate_results`, `failing_gate`, and `failing_reason`.
- **`src/planner.py`**: On `verify_res.passed == True`, the patch is applied and the model is refreshed. On `verify_res.passed == False`, the patch is:
  1. Rolled back (`.bak` restored).
  2. Downgraded to `suggestion_only`.
  3. Appended to `PlannerResult.suggestions` for manual review.
- **Trace Log**: Every `verify()` call records `gate_details` (full per-gate pass/fail list) and `failing_gate` in the structured trace log.

### Fail-Closed Guarantee
A patch that fails verification is **NEVER** auto-applied, even if originally tagged S0. The planner's `bak_path` restore ensures the file reverts to its pre-patch state.
